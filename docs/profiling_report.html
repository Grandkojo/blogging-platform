How the Recording Was Made

# 1. Start the application with profiling enabled
mvn spring-boot:run

# 2. Attach JFR to the running process
jps -l                            # find PID
jcmd <PID> JFR.start duration=120s filename=profiling_data_v2.jfr settings=profile

# 3. Analyse with the jfr CLI
jfr summary profiling_data_v2.jfr
jfr print --events jdk.ExecutionSample profiling_data_v2.jfr \
  | grep -oP '\w[\w.$]+\.\w[\w.$]+\(' \
  | sort | uniq -c | sort -rn | head -25

Finding 1 — CPU Hot Path (N+1 Eliminated)

Bottleneck Before: ClientPreparedStatement.<init> was the #1 CPU frame (24 of 258 samples ≈ 9 %). The MySQL JDBC driver was constructing a new PreparedStatement for every lazy-loaded user and tags relation, producing an N+1 query storm on each GET /posts call.

Fixed After: ClientPreparedStatement and StringInspector are completely absent from the hot frames. The only significant CPU hotspot is BCrypt.hashpw() (102 samples) — intentional, security-correct password hashing. CacheInterceptor.invoke() appears just once, confirming the Caffeine cache is short-circuiting DB access on read paths.

Optimisations applied: JOIN FETCH on PostRepository queries, @EntityGraph for eager association loading, spring.jpa.open-in-view=false (OSIV disabled), Caffeine @Cacheable on PostService and TagService.

Finding 2 — Garbage Collection Storm Eliminated

Bottleneck Before: 5 GC events in 120 s with heap cycling ~179 MB → ~62 MB per cycle (≈ 117 MB churn). The worst pause was 210 ms (G1Old mixed collection) — directly attributable to per-request byte[], ArrayList, and ResultSet objects generated by the N+1 query load.

Fixed After: Only 2 GC events recorded. The worst pause is 16.2 ms (CodeCache threshold, not application load). The G1Old collection that previously spiked to 210 ms is gone entirely.

Finding 3 — Heap Before / After GC

Heap snapshots confirm the reduction in object churn. Previously the heap had to be reclaimed by a mixed (Young + Old) collection. After optimisation, a single Young-gen sweep is sufficient and heap remains flat for the rest of the recording.

Heap Summary — GC #24 & #25 (Before → After)

Committed heap size: 188 MB. Heap after final GC: 62.9 MB — held flat. Previously, heapUsed bounced between ~179 MB and ~62 MB on every request cycle.

Finding 4 — Thread Sleeps: Async Notifications Confirmed

Bottleneck Before @Async: NotificationService.sendNotification() contained a simulated ~2-second Thread.sleep() executed on the HTTP worker thread (http-nio-8080-exec-*). Under load this blocked all request threads, serialising the entire API.

Fixed After @Async + ThreadPoolTaskExecutor: Every jdk.ThreadSleep event belongs to File Watcher (Spring DevTools) or container-0 (Tomcat internal). Zero http-nio-8080-exec threads appear in the sleep log — proving the notification work is fully offloaded to the async executor pool and HTTP workers are never blocked.

Optimisations applied: @Async on NotificationService, dedicated ThreadPoolTaskExecutor (core=4, max=10, queue=200), CompletableFuture for parallel post-detail fetching, ConcurrentHashMap + AtomicLong for lock-free view counting.

Finding 5 — JVM CPU Load (78 % Reduction)

Bottleneck Before: Peak JVM user-space CPU reached 47.95 % under the same request load. The spike was caused by the N+1 query storm driving the JDBC driver to parse statement strings in a tight loop.

Fixed After: Peak JVM CPU dropped to 10.32 % — a 78 % reduction. The workload is now dominated by genuine business logic (password hashing, JSON serialisation) rather than repeated SQL string construction.
